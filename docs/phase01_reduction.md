## 0. 앞선 단계까지의 맥락

Phase 0에서 두 개의 레버를 비교하기로 확정했습니다. 데이터 감축(DRR)과 계층화(f_tiered)입니다. Phase 0 7절에서는 **이중 감축 방지 가드**를 설계 원칙으로 세웠습니다. 선행 프로젝트의 Splunk 계수가 이미 애플리케이션 계층 압축을 반영하고 있으므로, 어레이 감축을 그 위에 곱하면 같은 압축을 두 번 세게 된다는 우려였습니다.

**Phase 1은 그 우려가 실제인지 확인하고, 감축 레버의 크기를 정하는 단계입니다.**

착수 시점의 계획은 두 갈래였습니다. 보증 약관을 확보하면 제외 데이터 조항을 근거로 삼고, 확보하지 못하면 워크로드별 실측 범위 조사로 전환한다는 것이었습니다. **약관 확보에 성공했으며, 결과적으로 두 갈래를 모두 수행했습니다.**

## 2. 보증 약관 원문 분석

Dell 공식 도메인에서 약관 전문을 확보했습니다(출처 1). 개정일 2026년 4월 24일, 시행일 2026년 5월 14일 판본입니다.

### 2.1 보증 배율은 제품군별로 상이

| 제품군 | 보증 배율 |
|---|---|
| PowerStore Gen 3 (1500·5500·9500) | 6배 |
| PowerStore Gen 2 (500T·1200T·3200T·3200Q·5200T·5200Q·9200) | 5배 |
| PowerMax 2500/8500 오픈 시스템 | 5배 |
| PowerMax 2500/8500 메인프레임(CKD) | 3배 |

**계획서 단계에서 인용한 "6:1"은 최상위 세대 한정 수치였습니다.** 보증 기간은 선불 유지보수 계약 기간과 동일합니다.

### 2.2 제외 데이터 — 본 단계의 핵심 조항

약관은 두 용어를 다음과 같이 정의합니다.

> **Unreducible Data**: 제품이 감축 불가로 식별한 데이터
> **Reducible Data**: 제품이 감축 가능으로 식별한 데이터

그리고 요건 2항에 다음이 명시됩니다.

> 보증은 Unreducible Data에 적용되지 않는다. Unreducible Data의 예에는 **호스트에서 압축된 데이터**, 호스트에서 암호화된 데이터, 오디오·이미지·PDF·비디오 파일이 포함되며 이에 한정되지 않는다.

**Phase 0 7절의 이중 감축 우려가 제조사 계약서로 확인되었습니다.** 호스트 측에서 이미 압축한 데이터는 보증 대상이 아니라고 벤더가 스스로 명문화하고 있습니다.

### 2.3 그 밖의 적용 요건

| # | 요건 |
|---|---|
| 1 | 물리 SSD 공간의 50% 이상에 데이터가 기록되기 전에는 보증이 발동하지 않음 |
| 2 | 압축·중복제거 기능이 지원되는 범위에서 모두 활성화되어 있어야 함 |
| 3 | 유상 지원 계약이 공백 없이 유지되어야 함 |
| 4 | PowerStore Gen 2는 PowerStoreOS 4.0 이상으로 최초 설치·연속 가동 조건 |

### 2.4 미달 시 구제 방식

현금 배상이 아닙니다. Dell이 시스템 튜닝, 마이크로코드 재구성, 추가 하드웨어 제공 중 하나를 **자사 재량으로** 선택해 시정하며, 추가 용량은 제품 물리 용량의 50%를 넘지 않습니다. 청구는 제품당 1회로 제한되고, 보증 기간 만료 전에 서면으로 접수해야 합니다.

약관은 또한 **특정 감축률이 달성됨을 보증하는 것이 아니라, 미달 시 고객이 받을 구제 수단을 규정한 것**이라고 명시합니다. 이 문장은 Phase 7(정량화 불가 요인)에서 다시 다룹니다.

## 3. 감축 대상 판정 방식

### 3.1 조사한 질문

약관의 제외 목록이 확장자 기반의 정적 목록인지, 아니면 실시간 측정 결과인지에 따라 파라미터 처리 방식이 달라집니다. Splunk의 압축 파일은 표준 확장자를 갖지 않으므로, 정적 목록이라면 감축 대상으로 잘못 분류될 수 있기 때문입니다.

### 3.2 확인 결과 — 런타임 분류

약관의 정의가 **"제품이 식별한(identified by the Product)"** 이라는 표현을 쓰고 있으며, 예시 목록에 "이에 한정되지 않는다"는 단서가 붙어 있습니다. 즉 확장자 목록이 아니라 **어레이가 실제로 처리해 보고 판정하는 구조**입니다.

이를 뒷받침하는 사실을 제조사 자료에서 확인했습니다.

| 확인 내용 | 출처 |
|---|---|
| PowerStore는 인라인 방식으로 데이터가 유입될 때 각 노드가 감축을 수행 | 출처 2 |
| 압축 알고리즘은 DEFLATE(LZ77 + 허프만)이며, CPU 부하가 크므로 전용 가속 칩으로 오프로드 | 출처 2 |
| 감축 순서는 영값 탐지 → 중복제거 → 압축 → 2MB 스트라이프 기록이며, 쓰기 캐시에서 드라이브로 내려갈 때 수행 | 출처 4 |
| 4.0 판부터 시스템의 **감축 가능·불가 데이터 양을 사용자가 확인할 수 있는 도구**를 제공 | 출처 3 |

마지막 항목이 결정적입니다. **감축 가능 여부를 표시하는 도구가 존재한다는 것은 어레이가 그 값을 실측한다는 뜻**이며, 정적 목록이 아님을 확인해 줍니다.

### 3.3 이 결과가 파라미터에 주는 의미

판정이 런타임 실측이므로 **`drr_precompressed`의 값을 벤더 문서에서 읽어낼 수 없습니다.** 고객 환경마다 다르고, 어레이가 측정합니다.

그러나 **판정의 방향은 물리적으로 결정됩니다.** DEFLATE로 이미 압축된 데이터에 다시 DEFLATE를 적용하면 추가 감축이 거의 발생하지 않습니다. 압축은 반복 패턴을 짧은 기호로 치환하는 방식인데, 이미 치환이 끝난 데이터에는 남은 패턴이 거의 없기 때문입니다.

따라서 `drr_precompressed`는 **1.0 부근으로 수렴한다고 도출(derived)할 수 있으나, 실측값은 아닙니다.**

## 4. Splunk 데이터의 감축 가능성

### 4.1 어레이에 도달하는 데이터의 구성

선행 프로젝트에서 검증한 Splunk 저장 구조입니다(출처 5).

| 구성 요소 | 원본 대비 비중 | 상태 |
|---|---|---|
| rawdata | 0.15 | **압축된 형태로 저장됨** |
| tsidx (색인) | 0.35 | 색인 용어 파일 |
| 합계 | 0.50 | |

Splunk 공식 문서는 rawdata 파일이 **압축된 형태(in a compressed form)** 로 저장된다고 명시합니다. 커뮤니티 자료에서도 클러스터 복제 시 전송되는 것이 압축된 rawdata(journal.gz)라는 서술이 확인됩니다(출처 6).

**즉 어레이가 보는 논리 용량 0.50 가운데 0.15는 이미 압축이 끝난 데이터입니다.**

### 4.2 혼합 감축률 도출

rawdata의 어레이 감축률을 1.0(감축 없음), tsidx의 감축률을 `d`라 하면, 어레이가 인식하는 감축률은 다음과 같습니다.

```
혼합 DRR = 0.50 / (0.15 + 0.35 / d)
```

| tsidx 감축률 d | 혼합 DRR | 비고 |
|---|---|---|
| 1.0 (감축 없음) | **1.00** | 하한 |
| 1.5 | 1.30 | |
| 2.0 | 1.54 | |
| 3.0 | 1.88 | |
| 4.0 | 2.11 | |
| 6.0 | **2.40** | 보증 배율만큼 색인이 줄어드는 낙관적 경우 |
| 무한대 | **3.33** | **색인이 완전히 사라져도 넘을 수 없는 절대 상한** |

**절대 상한이 3.33:1입니다.** 색인 파일이 0바이트로 압축된다는 물리적으로 불가능한 가정을 해도 6:1에 도달하지 못합니다. rawdata 0.15가 감축되지 않는 한 분모가 0.15 아래로 내려갈 수 없기 때문입니다.

### 4.3 아카이브 계층에서는 감축이 작동하지 않습니다

선행 프로젝트에서 검증한 대로, 아카이브(frozen) 단계에서는 색인이 제거되고 rawdata만 남습니다. 즉 아카이브 계층의 구성은 **압축된 rawdata 단독**입니다.

위 식에 대입하면 tsidx 항이 사라지므로 감축률은 **정확히 1.00**입니다.

> **본 단계에서 가장 중요한 발견입니다.**
> **감축이 가장 작동하지 않는 데이터가, 계층화가 겨냥하는 바로 그 데이터입니다.**
> 두 레버가 같은 데이터를 향하지만 그중 하나만 작동합니다.

### 4.4 이 도출의 한계

세 가지를 명시합니다.

1. **rawdata 감축률 1.0은 도출값이며 실측이 아닙니다.** 서로 다른 버킷에 동일한 로그 행이 반복되는 경우 블록 중복제거가 일부 작동할 여지가 있습니다. 다만 압축 결과물은 무작위성이 높아 블록 단위 일치가 발생하기 어려우므로, 1.0을 기준으로 두고 상한을 소폭 열어 둡니다.
2. **tsidx의 압축 가능성은 미확인입니다.** 색인 파일의 내부 구조와 자체 압축 여부에 관한 공식 자료를 확보하지 못했습니다. 범위를 넓게 두고 민감도 1순위로 처리합니다.
3. **Splunk 계수 자체가 데이터 종류에 따라 변동합니다.** 공식 문서도 데이터 원본의 구조와 필드에 따라 압축률이 달라지며 총계 기준 50%를 권장 추정치로 쓴다고 서술합니다. 혼합 DRR 식은 이 권장 추정치 위에 서 있습니다.

## 5. 파라미터 확정

| 파라미터 | 값 | status | confidence | 근거 |
|---|---|---|---|---|
| `drr_guarantee_gen3` | 6.0 | confirmed | vendor | 약관 (출처 1) |
| `drr_guarantee_gen2` | 5.0 | confirmed | vendor | 약관 (출처 1) |
| `drr_rawdata` | low 1.00 / base 1.00 / high 1.20 | partial | derived | 4.2·4.4절 |
| `drr_tsidx` | low 1.00 / base 2.00 / high 6.00 | **assumed** | assumption | 미확인. **민감도 1순위** |
| `drr_blended_searchable` | 계산값 (1.00 ~ 2.40) | derived | derived | 4.2절 식 |
| `drr_blended_archive` | 1.00 | derived | derived | 4.3절 |
| `drr_ceiling` | 3.33 | derived | derived | 4.2절 절대 상한 |

**`drr_blended_*`는 원장에 상수로 등재하지 않고 함수로 계산합니다.** 상수로 적으면 Splunk 계수가 바뀔 때 값이 어긋나는데, 선행 프로젝트에서 구버전 수치가 이월된 사례가 있었기 때문입니다.

**`drr_tsidx`의 base를 2.00으로 둔 이유:** 근거가 없으므로 중앙값을 임의로 정할 수 없습니다. 다만 계산을 진행하려면 기준값이 필요하므로, 범위의 하한 쪽에 가깝게 두어 **감축 레버를 과대평가하지 않는 방향**으로 설정했습니다. 이 선택 자체가 민감도 분석 대상입니다.

| 4 | 구제 방식의 경제적 가치 | 현금 배상이 아닌 튜닝·하드웨어 제공이며 1회 한정 | Phase 7로 이관 |

**참고 자료로만 기록하는 수치:** 워크로드 유형별 감축률 격차로 가상머신 환경 10:1~15:1, 구조화된 보안 로그 중간 수준, 패킷 캡처 미미라는 서술이 있습니다(출처 7). 본 프로젝트의 계산에는 사용하지 않으며, 다른 워크로드에서 결론이 달라질 수 있음을 보이는 근거로만 인용합니다.

## 9. 이 결과가 프로젝트에 미치는 영향

### 9.1 가설 H1이 강화되었습니다

Phase 0의 가설 H1은 "감축의 이득 상한은 나눗셈 6, 계층화의 이득은 나눗셈 R(약 22)"이었습니다. **감축의 상한이 6이 아니라 3.33, 현실적으로는 1.00~2.40으로 확인되었으므로 격차가 더 벌어졌습니다.**

### 9.2 동시에 리스크 R4가 커졌습니다

결론이 자명해질 위험입니다. 감축이 1.00~2.40이고 계층화가 22배라면 전환점 탐색 자체가 무의미해질 수 있습니다.

**대응:** Phase 0의 반증 조건(6.3절)을 더 엄격하게 검증해야 합니다. 즉 **계층화가 제약되는 구간(f_tierable이 낮은 경우)이 실제로 존재하는지**를 확인하는 것이 이제 프로젝트의 성패를 가릅니다. 계층화 가능 비율이 낮으면 22배라는 이득이 적용될 대상이 없어지므로, 감축이 작은 값이어도 유일한 수단이 됩니다.

**따라서 Phase 3(배치 설계)의 무게가 커졌습니다.** 당초에는 단순 배치 로직이었으나, 이제는 "무엇을 내려보낼 수 있는가"의 제약 조건을 정하는 단계가 되었습니다.

### 9.3 서술의 축이 바뀝니다

Phase 8에서 쓸 문장이 달라집니다.

| 구분 | 내용 |
|---|---|
| 당초 예상 | "감축과 계층화 중 어느 쪽이 유리한지는 단가 배수에 따라 달라진다" |
| Phase 1 이후 | "본 워크로드에서 감축은 구조적 상한이 낮으며, 그 상한은 데이터 자체의 성질에서 나온다" |

이 서술은 특정 제품을 깎아내리는 것이 아닙니다. 6:1 보증은 감축 가능한 데이터에서는 유효하며, 다만 **로그 워크로드가 그 범주에 들지 않는다**는 사실을 말하는 것입니다. 벤더 중립 서술 원칙에 부합합니다.

## 12. 후속 단계

Phase 2는 **매체 가격 원장 구축**입니다. Phase 1의 결과가 Phase 2의 우선순위를 바꾸지는 않으나, Phase 3의 성격이 달라졌습니다.

| Phase | 당초 성격 | Phase 1 이후 |
|---|---|---|
| 2 | 매체 단가 수집 | 변동 없음 |
| 3 | 계층 배치 로직 구현 | **"무엇을 내려보낼 수 있는가"의 제약 조건 확정** — 비중 상승 |

9.2절에서 밝힌 대로, 감축 레버가 작다는 사실이 확인되면서 **계층화 가능 비율(`f_tierable`)이 결론을 좌우하는 유일한 변수에 가까워졌습니다.** Phase 3에서 이 값의 근거를 확보하지 못하면 프로젝트 전체가 하나의 가정값 위에 서게 됩니다.

Phase 2 착수 전에 이 점을 Phase 0 리스크 목록에 반영해야 합니다.
